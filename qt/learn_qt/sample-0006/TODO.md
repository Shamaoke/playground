
# Sample 0006 — план работ #

Учебный проект: имитация автоматизированной системы управления тепловозом.
Участники: `rack` (стоечная программа, УОИ) и `display` (дисплейная программа,
ДМ), общий протокол — `protocol`.

Задачи упорядочены по приоритету — от наиболее к наименее приоритетным. Главная
цель проекта — научиться описывать сетевое взаимодействие, поэтому сначала идёт
проектирование протокола, затем инфраструктура, затем реализация участников
(подход contract-first).

Уже решено:

* транспорт — UDP, кадр — 1350 байт, обязательная проверка CRC;

* словарь данных — `protocol/protocol.xml`, C++-код генерируется из него на этапе сборки;

* `rack` — современный C++, RAII-обёртки над POSIX-сокетами, без Qt;

* `display` — Qt/QML, сеть средствами Qt;

* сборка — CMake + Ninja + clang++;

* модель «клиент-сервер» не используется: устройства называются по предметной
  области (`rack`, `display`), роли — по логическим каналам;

* логические каналы маркируются в кадре явно;

* визитка (объявление устройства) обязательна.

Теория и обзор подходов — в личной документации: [Сетевое взаимодействие в промышленных системах](https://shamaoke.github.io/summaries/industrial_networking).

## Этап I. Проектирование протокола ##

### 1. Выбор способа маркировки логических каналов ###

**Описание.** Окончательно выбрать между вариантами A (кадр = канал), B (блоки
TLV) и C (фиксированные области + флаги) и определить формат блока.

**Решение** (подробно — в `PROTOCOL.md`).

* Способ маркировки — **B**: кадр из блоков TLV.

* Блок: `type` — 1 байт, `length` — 2 байта LE (длина только `value`),
  `length = 0` допустим, без выравнивания, без собственной версии.

* Конец последовательности блоков — длина полезной нагрузки в заголовке кадра
  **и** зарезервированный `type = 0x00` (заполнение нулями); признаки должны
  быть согласованы.

* Разбор: неизвестный тип — пропустить; выход `length` за пределы, `0x00`
  внутри нагрузки, `0xFF` — отвергнуть кадр; повторяющиеся типы допустимы.

* Идентификаторы: `0x00` — конец / заполнение, `0x01` — объявление, `0x02` —
  образ процесса, `0x03` — событие, `0x04` — квитанция, `0x05` — команды,
  `0xFF` — зарезервирован.

### 2. Заголовок кадра и общая раскладка ###

**Описание.** Расписать побайтно, что есть в каждом кадре независимо от канала:
сигнатура, версия протокола, отправитель, порядковый номер кадра, длина
полезной нагрузки, заполнение, CRC.

**Предложения.**

* Сигнатура (magic) — 2 байта.

* Версия протокола — 2 байта, берётся из `version` в `protocol.xml`.

* Тип узла (`rack` / `display`) и его идентификатор.

* Порядковый номер кадра — `uint32`, для подсчёта потерь.

* Длина полезной нагрузки (следует из решения по задаче 1).

* Все числа — little-endian.

* CRC-16/CCITT-FALSE — последние 2 байта из 1350.

* Результат записать в `PROTOCOL.md`, раздел «Заголовок кадра».

Задачи 1 и 2 образуют «скелет» кадра — их удобно решать вместе.

### 3. Канал объявления устройства (визитка) ###

**Описание.** Определить содержимое визитки, частоту отправки и правила контроля
связи.

**Предложения.**

* Содержимое: тип узла, идентификатор, имя, версия ПО, признак главного ДМ.

* Частота: например, 1 раз в секунду.

* Таймаут потери связи: например, 3 пропущенные визитки. Счётчик назвать
  честно — `last_seen` или `silence_counter`, а не `ttl`, чтобы не путать с
  IP TTL.

* Индикатор «связь есть / нет» на дисплее — первая видимая функция для QML.

### 4. Канал событий ###

**Описание.** Спроектировать надёжную доставку событий стойки на ДМ: очередь,
номер события, квитанция, повтор, устранение дубликатов.

**Предложения.**

* Начать со **Stop-and-Wait с попутной передачей**, как в `tem18lng`, но с
  исправленными недостатками:

  + устранение дубликатов по номеру, а не по тексту;

  + отдельное поле реального времени события;

  + текст в UTF-8.

* Позже, в качестве упражнения, перейти на кумулятивное квитирование.

* Отдельно продумать, что делать, если квитируют оба ДМ.

### 5. Канал команд пульта и главный ДМ ###

**Описание.** Определить, какие команды передаёт ДМ, нужна ли им надёжная
доставка, как назначается главный ДМ и как стойка отвергает команды от второго.

**Предложения.**

* Сначала разобрать, как это сделано в боевом коде: `isMain`, `Block`, логика
  `VCU1_PU1` / `VCU2_PU2` и `countDM` в `tem18lng-rack/source/dmnet.cpp`.

* Затем выбрать модель:

  + команды как **состояние** — ДМ циклически передаёт текущее положение
    органов управления, повторы не нужны (боевой код, судя по флагам `_trig`,
    использует эту модель с выделением фронтов);

  + команды как **события** — с квитированием.

## Этап II. Описание протокола в коде ##

### 6. Расширение `protocol.xml` ###

**Описание.** Превратить словарь данных в полную спецификацию, из которой можно
генерировать код.

**Предложения.**

* Добавить тип значения (`int16` / `uint16` / …), чтобы было ясно, знаковое ли
  значение.

* Добавить описание каналов и их идентификаторов.

* Смещения `<byte>` отсчитывать от начала блока образа процесса.

* Возможно, добавить XSD-схему для проверки XML (необязательно).

### 7. Каркас сборки CMake ###

**Описание.** Корневой `CMakeLists.txt` с подпроектами `protocol` (статическая
библиотека), `rack`, `display` и `CMakePresets.json`.

**Предложения.**

* По образцу `sample-0005`: preset `debug`, Ninja, `clang++`,
  `CMAKE_EXPORT_COMPILE_COMMANDS`.

* `protocol` — без зависимости от Qt, чтобы его могли использовать обе
  программы.

* Задача небольшая, её можно сделать в любой момент.

### 8. Генератор кода XML → C++ ###

**Описание.** Выбрать инструмент и встроить генерацию в сборку.

**Предложения.**

* Сравнить варианты: Ruby (REXML), Python, маленькая C++-утилита в том же
  CMake-проекте.

* Встраивание — через `add_custom_command(OUTPUT …)` с зависимостью от
  `protocol.xml`.

* На выходе — заголовок с `constexpr`-таблицей дескрипторов и константами
  идентификаторов каналов.

### 9. Протокольная библиотека ###

**Описание.** Сериализация и разбор кадра и блоков, CRC, преобразование
raw ↔ value, unit-тесты. Сюда же входит доработка текущих `ParameterDescriptor`
и `Protocol`.

**Предложения.**

* Замечания по текущему коду: `std::move` в конструкторах, агрегат с
  designated initializers, `findById` с возвратом указателя и проекцией
  (`std::ranges::find(items, id, &ParameterDescriptor::getId)`), валидация.

* Часть замечаний может отпасть: если дескрипторы будут генерироваться как
  `constexpr`, классы, скорее всего, станут проще.

* Первый тест — check value CRC: `"123456789"` → `0x29B1`.

* Побайтная сериализация через `std::span<const std::byte>`, без
  `reinterpret_cast` к упакованным структурам.

## Этап III. Реализация участников ##

### 10. `rack`: стоечная программа ###

**Описание.** RAII-обёртки над POSIX-сокетами, цикл публикации кадров, имитация
данных узлов тепловоза.

**Предложения.**

* Move-only класс `Socket`, ошибки — через исключения или `std::expected`.

* Начать с unicast на `localhost`, широковещательную рассылку добавить позже
  отдельным шагом.

* Имитация данных — простые генераторы (например, синусоида давления).

### 11. `display`: дисплейная программа ###

**Описание.** Приём кадров через `QUdpSocket`, разбор протокольной библиотекой,
отображение в QML.

**Предложения.**

* Чтение — в цикле `while (hasPendingDatagrams())`.

* Модель данных — `QObject` со свойствами, как в `sample-0005`.

* Первые экраны: индикатор связи, пара величин, журнал событий.

## Отложено ##

| Тема | Почему отложено |
|---|---|
| Квитирование аварий машинистом (ISA-18.2) | решено пока не разбирать |
| Многосекционные тепловозы и СМЕ | начинаем с одной стойки |
| Цикл работы стоечной программы (как ПЛК) | полезно для понимания, но не блокирует проектирование |
