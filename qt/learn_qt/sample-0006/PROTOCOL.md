
# Sample 0006 — спецификация протокола #

Протокол обмена между стоечной программой (`rack`) и дисплейной программой
(`display`). Документ фиксирует принятые решения, обоснования и обзор
альтернатив — в личной документации: [Сетевое взаимодействие в промышленных системах](https://shamaoke.github.io/summaries/industrial_networking).

Статус: **черновик**. Разделы, помеченные «не определено», будут заполнены по
мере выполнения задач из `TODO.md`.

## Общие положения ##

* Транспорт — UDP.

* Размер кадра — фиксированный, **1350 байт**.

* Порядок байтов всех многобайтовых чисел — **little-endian**.

* Целостность кадра контролируется **CRC** (алгоритм не определён — задача 9 в `TODO.md`).

* Логические каналы маркируются в кадре **явно**: кадр состоит из заголовка и
  последовательности блоков TLV (type-length-value), каждый блок принадлежит
  одному логическому каналу.

* Оба узла (`rack` и `display`) передают кадры **циклически**, через заданные
  промежутки времени. Отдельного канала объявления устройства (визитки) нет
  (см. «Контроль связи»).

## Структура кадра ##

```
┌───────────┬─────────┬─────────┬─────┬─────────┬────────────┬─────┐
│ Заголовок │ Блок 1  │ Блок 2  │ ... │ Блок N  │ Заполнение │ CRC │
└───────────┴─────────┴─────────┴─────┴─────────┴────────────┴─────┘
            └───────── полезная нагрузка ───────┘
```

Полезная нагрузка — последовательность блоков от конца заголовка до начала
заполнения. Её длина указывается в заголовке кадра.

Заполнение — байты `0x00` до позиции CRC.

## Заголовок кадра ##

```
┌─────────┬─────────┬──────────┬────────┬────────────────┬───────────────┐
│ magic   │ version │ nodeType │ nodeId │ sequenceNumber │ payloadLength │
│ 2 байта │ 1 байт  │ 1 байт   │ 1 байт │ 4 байта, LE    │ 2 байта, LE   │
└─────────┴─────────┴──────────┴────────┴────────────────┴───────────────┘
```

| Поле             | Размер      | Описание                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
|------------------|-------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `magic`          | 2 байта     | Сигнатура протокола: `0x50 0x54` (ASCII `"PT"`, от «PULT» — то, с помощью чего управляют тепловозом, система управления). Позволяет быстро отличить кадр протокола от случайного трафика на том же UDP-порту.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `version`        | 1 байт      | Версия **формата кадра** (структура заголовка, формат TLV-блока, идентификаторы каналов). Текущее значение — `1`. Увеличивается только при структурных изменениях формата: добавление параметров в словарь данных или новых каналов версии не требует (обеспечено прямой совместимостью TLV). Не путать с версией словаря данных `protocol.xml` — она передаётся в блоке образа процесса (канал `0x01`, задача 6).                                                                                                                                                                                                                                                                                                 |
| `nodeType`       | 1 байт      | Тип узла-отправителя. `0x00` и `0xFF` зарезервированы (недопустимые значения — та же защита от неинициализированной/стёртой памяти, что и у идентификаторов каналов). `0x01` — `rack`, `0x02` — `display`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `nodeId`         | 1 байт      | Идентификатор узла, уникальный в рамках своего `nodeType` (не глобально). Допустимые значения — `0x01`–`0xFE`; номера совпадают с нумерацией узлов в кабине и документации. Например: `rack` — всегда `1` (пока единственная стойка); `display` — `1` для первого ДМ, `2` — для второго. `0x00` недопустим: это значение по умолчанию, и узел с непрочитанной или повреждённой конфигурацией не должен выйти в сеть под «правильным» адресом. `0xFF` зарезервирован под адрес «все узлы данного типа» в полях адресата внутри блоков; в заголовке (как отправитель) недопустим. Признак главного ДМ (`isMain`) не хранится здесь — он может меняться во время работы; способ его передачи определяется в задаче 5. |
| `sequenceNumber` | 4 байта, LE | Порядковый номер кадра от этого отправителя; используется получателем для подсчёта потерь. Увеличивается на каждый отправленный кадр, начиная с запуска узла. Переполнение `uint32` при разумной частоте отправки не является практической проблемой.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `payloadLength`  | 2 байта, LE | Длина полезной нагрузки в байтах (см. «Конец последовательности блоков»).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

Размер заголовка — **11 байт** (`H = 11`).

Правила:

* `magic` и `version` — единственные поля заголовка, чьи размер и положение
  зафиксированы навсегда, независимо от последующей эволюции формата. Это
  решает проблему начальной интерпретации (bootstrapping): получатель должен
  быть способен прочитать версию формата, не зная заранее, как именно этот
  формат изменился.

* Несовпадение `magic` или `version` с ожидаемыми значениями — отказ от кадра
  целиком, тем же принципом «всё или ничего», что и при несовпадении CRC
  (см. «Правила разбора»).

## Контроль связи ##

Отдельного канала объявления устройства (визитки, как `pktType = 0` в
`tem18lng`) в протоколе **нет**. Её функции выполняются заголовком кадра и
циклической передачей кадров:

| Функция                               | Чем обеспечивается                                                           |
|---------------------------------------|------------------------------------------------------------------------------|
| Идентификация отправителя             | поля `nodeType` и `nodeId` заголовка каждого кадра                           |
| Объявление (discovery)                | первый корректный кадр от новой пары `nodeType` / `nodeId`                   |
| Проверка жизнеспособности (heartbeat) | любой корректный кадр от узла                                                |
| Описание формата данных               | раскладка известна обеим сторонам при сборке (словарь данных `protocol.xml`) |

Сведения, которые в `tem18lng` передавались в визитке, распределены по
каналам, где они используются: версия словаря данных — в блоке образа процесса
(задача 6), признак главного ДМ — в канале команд пульта (задача 5).

Правила:

* Каждый узел передаёт кадры циклически, даже если ему нечего передать. В этом
  случае передаётся кадр с пустой полезной нагрузкой (`P = 0`): только
  заголовок, заполнение и CRC.

* Период передачи кадров и таймаут потери связи не определены (задача 3).

## Блок ##

```
┌──────────┬────────────┬──────────────────────────┐
│ type     │ length     │ value                    │
│ 1 байт   │ 2 байта LE │ length байт              │
└──────────┴────────────┴──────────────────────────┘
```

| Поле     | Размер        | Описание                                                        |
|----------|---------------|-----------------------------------------------------------------|
| `type`   | 1 байт        | идентификатор логического канала (см. «Идентификаторы каналов») |
| `length` | 2 байта, LE   | длина поля `value` в байтах, **без учёта** заголовка блока      |
| `value`  | `length` байт | данные канала; формат определяется типом блока                  |

Правила:

* Размер заголовка блока — 3 байта.

* `length = 0` допустим (блок без данных). Такой блок применяется, когда
  информацию несёт сам факт присутствия блока, а не его содержимое.

  Возможные случаи:

  | Пример блока             | Направление                   | Смысл присутствия блока                                               |
  |--------------------------|-------------------------------|-----------------------------------------------------------------------|
  | Запрос полного состояния | `display` -> `rack`           | прислать всё, включая накопленные события, после восстановления связи |
  | Снятие главенства        | `display` (главный) -> `rack` | ДМ отказывается от роли главного (например, перед выключением)        |
  | Очередь событий пуста    | `rack` -> `display`           | явное подтверждение, что неквитированных событий нет                  |

  Аналогичный приём используется в TLS (пустые расширения
  `extended_master_secret`, `encrypt_then_mac`) и DHCP (опция Rapid Commit).

  Блоки без данных разрешены сразу, а не по мере необходимости: если запретить
  их сейчас, программы старых версий будут отвергать кадры с такими блоками
  целиком, что нарушит прямую совместимость.

* Поле `value` может содержать произвольные байты, включая `0x00` и `0xFF`:
  ограничения на значения `0x00` и `0xFF` относятся только к полю `type`.
  Разборщик не анализирует содержимое `value`, а перешагивает через него по
  `length`.

* Блоки **не выравниваются**: каждый следующий блок начинается сразу после
  предыдущего. Разбор выполняется побайтно.

* Отдельной версии у блока нет; формат блока определяется версией протокола
  в заголовке кадра.

## Конец последовательности блоков ##

Используются два независимых признака:

1. **Длина полезной нагрузки** из заголовка кадра — разбор продолжается, пока не
   будет достигнут её конец.

2. **Тип `0x00`** зарезервирован как «конец / заполнение». Поскольку заполнение
   состоит из байтов `0x00`, конец последовательности блоков обозначается
   автоматически.

Признак `0x00` проверяется только в позиции поля `type`, то есть там, где мог бы
начаться следующий блок. Заполнение — не блок: у него нет поля `length`, и
разборщик, встретив `0x00` в позиции `type`, прекращает обход блоков.

Оба признака должны быть согласованы. Обозначения на схеме кадра:

```
0             H                     E                       C        1350
├─────────────┼─────────────────────┼───────────────────────┼────────┤
│ Заголовок   │ Полезная нагрузка   │ Заполнение            │ CRC    │
│             │ блок 1 … блок N     │ 0x00 … 0x00           │        │
└─────────────┴─────────────────────┴───────────────────────┴────────┘
              ├───────── P ─────────┤
```

| Обозначение | Значение                                                  |
|-------------|-----------------------------------------------------------|
| `H = 11`    | размер заголовка кадра; смещение начала полезной нагрузки |
| `P`         | длина полезной нагрузки из заголовка кадра                |
| `E = H + P` | смещение конца полезной нагрузки (начала заполнения)      |
| `C = 1348`  | смещение поля CRC                                         |

Кадр согласован, если выполняются **все** условия:

| № | Условие                                       | Смысл                                                                                     |
|---|-----------------------------------------------|-------------------------------------------------------------------------------------------|
| 1 | `E ≤ C`                                       | Полезная нагрузка помещается перед CRC                                                    |
| 2 | Обход блоков от `H` заканчивается точно в `E` | Ни один блок не выходит за `E`, в конце нагрузки нет обрывка заголовка блока              |
| 3 | На отрезке `[H, E)` нет блока с `type = 0x00` | Маркер конца не встречается внутри полезной нагрузки                                      |
| 4 | Все байты на отрезке `[E, C)` равны `0x00`    | Заполнение начинается сразу за нагрузкой и не содержит мусора; при `E = C` не проверяется |

При нарушении любого условия кадр отвергается.

Проверки согласованности дополняют CRC: CRC защищает от искажений при
передаче, а проверки согласованности — от ошибок отправителя (неверно
вычисленная длина, переиспользованный необнулённый буфер и т. п.).

## Формирование кадра ##

Кадр формирует отправитель в следующем порядке (обозначения — см. «Конец
последовательности блоков»):

| Шаг | Действие                                                          | Результат               |
|-----|-------------------------------------------------------------------|-------------------------|
| 1   | записать блоки подряд, начиная со смещения `H`                    | известна позиция `E`    |
| 2   | записать в заголовок кадра `P = E − H` и остальные поля заголовка | заголовок заполнен      |
| 3   | заполнить отрезок `[E, C)` байтами `0x00`                         | заполнение сформировано |
| 4   | вычислить CRC по отрезку `[0, C)` и записать его в `[C, 1350)`    | кадр готов к отправке   |

Правила:

* Длина полезной нагрузки `P` становится известна только после записи всех
  блоков, поэтому поле длины в заголовке заполняется после них.

* Заполнение записывается **явно** на каждом кадре, независимо от того, как
  был получен буфер. Нельзя полагаться на то, что буфер был обнулён ранее:
  при переиспользовании буфера в заполнении останутся данные предыдущего
  кадра, и получатель отвергнет кадр (см. условие 4 согласованности).

* CRC вычисляется **последним**: он покрывает заголовок, полезную нагрузку и
  заполнение. Любое изменение кадра после вычисления CRC делает кадр
  недействительным.

Требование к заполнению (все байты `0x00`) обосновано следующим:

| Довод                    | Пояснение                                                                                                                |
|--------------------------|--------------------------------------------------------------------------------------------------------------------------|
| Обнаружение ошибок       | ненулевой байт в заполнении указывает на ошибку отправителя: необнулённый буфер, заниженная `P`, запись за границу блока |
| Отсутствие утечек памяти | мусор в заполнении — это содержимое памяти отправителя, уходящее в сеть (ср. уязвимость Etherleak, CVE-2003-0001)        |
| Детерминированность      | одинаковое содержимое кадра даёт одинаковые байты и одинаковый CRC; захваты трафика сравниваются напрямую                |

## Правила разбора ##

Кадр принимается или отвергается **целиком** («всё или ничего»): если любая
проверка не пройдена, не обрабатывается ни один блок кадра, включая корректно
разобранные до места ошибки.

Разбор выполняется в две фазы:

1. **Проверка.** Проверки выполняются в порядке возрастания стоимости: размер
   датаграммы, заголовок кадра, CRC, обход блоков и согласованность. В этой
   фазе состояние программы не изменяется; для каждого блока запоминаются только
   его тип и границы поля `value`.

2. **Обработка.** Только если все проверки пройдены, каждый блок передаётся
   обработчику своего логического канала.

Отвергнутый кадр обрабатывается так, как если бы он не был получен: состояние
программы не изменяется, увеличивается счётчик ошибок по причине отвергания,
делается запись в журнал (с ограничением частоты).

| Ситуация                                                 | Действие                                      |
|----------------------------------------------------------|-----------------------------------------------|
| Размер датаграммы не равен 1350 байт                     | отвергнуть кадр целиком                       |
| Байты `magic` не совпадают с ожидаемыми                  | отвергнуть кадр целиком                       |
| `version` заголовка не совпадает с ожидаемым             | отвергнуть кадр целиком                       |
| `nodeType` равен `0x00` или `0xFF`                       | отвергнуть кадр целиком                       |
| `nodeId` равен `0x00` или `0xFF`                         | отвергнуть кадр целиком                       |
| CRC не совпадает                                         | отвергнуть кадр целиком                       |
| Полезная нагрузка не помещается перед CRC                | отвергнуть кадр целиком                       |
| Остаток нагрузки меньше 3 байт (обрывок заголовка блока) | отвергнуть кадр целиком                       |
| Блок с `type = 0x00` в пределах полезной нагрузки        | отвергнуть кадр целиком                       |
| Блок с `type = 0xFF`                                     | отвергнуть кадр целиком                       |
| `length` выходит за пределы полезной нагрузки            | отвергнуть кадр целиком                       |
| Обход блоков не заканчивается точно на конце нагрузки    | отвергнуть кадр целиком                       |
| Заполнение содержит байт, отличный от `0x00`             | отвергнуть кадр целиком                       |
| Блок неизвестного типа                                   | пропустить по `length` (прямая совместимость) |
| Несколько блоков одного типа                             | допустимо; порядок блоков сохраняется         |

## Идентификаторы каналов ##

| `type`        | Канал                                 | Направление        |
|---------------|---------------------------------------|--------------------|
| `0x00`        | зарезервирован: конец / заполнение    | —                  |
| `0x01`        | образ процесса                        | `rack` → `display` |
| `0x02`        | событие                               | `rack` → `display` |
| `0x03`        | квитанция на событие                  | `display` → `rack` |
| `0x04`        | команды пульта                        | `display` → `rack` |
| `0x05`–`0xFE` | свободны для будущих каналов          | —                  |
| `0xFF`        | зарезервирован: недопустимое значение | —                  |

`0xFF` зарезервирован потому, что неинициализированная память и стёртая
флеш-память часто заполнены `0xFF`: такой блок сразу распознаётся как
недопустимый.

## Каналы ##

### Образ процесса (`0x01`) ###

Не определено. Раскладка значений задаётся словарём данных
`protocol/protocol.xml`; смещения отсчитываются от начала поля `value` блока.
В начале поля `value` предполагается версия словаря данных (задача 6).

### Событие (`0x02`) и квитанция (`0x03`) ###

Не определено (задача 4).

### Команды пульта (`0x04`) ###

Не определено (задача 5).
